# Local Ollama bots and comparison

Ollama is an optional, local decision service, not a training algorithm. Install Ollama on the computer running the Vite dev server, start it, and install the model named in **Settings → Bots** (default `qwen3:8b`). Use **Test Ollama connection** there and save settings. Open the game on `localhost` or `127.0.0.1`; the local-only bridge is intentionally unavailable on the static site, over a LAN, or from the Arena cloud preview. Restart the Vite server after updating the project. Ollama and its selected model are separate installations and are not bundled with the game.

In **Your table**, choose a style per bot seat. The default uses Settings/deck style; any seat can instead choose Balanced, another heuristic, the saved trained or neural policy, or Ollama. Several seats may use Ollama: they share the local service/model, but each request has only the acting seat's masked `PlayerView`. A seat's style is retained by a save; the model tag is a local setting and is not embedded in the save. Hosts run bots for online tables, so Ollama must run on the host's computer. The trained/neural selections use their existing fallback if the corresponding saved profile is missing.

The Ollama agent includes relevant short rule summaries and printed text for cards visible to the acting player. These are automatically selected context, **not** a full rulebook upload or interactive rule-search tools. The prompt contains the legal option IDs; the model picks an ID and never mutates the game. The engine remains the authority. A failed block that cannot currently succeed is excluded when an alternative exists (same safety rule used by the heuristic bot). Single or forced safe choices do not call the LLM. Other choices normally do, except when the essential prompt exceeds the size budget or the service is in a fallback cooldown; several Ollama seats may make a game slow. Malformed responses and illegal IDs are retried up to three times with a constrained JSON schema, a larger output budget, and slight sampling on retries. If all retries fail, or the service is unavailable or times out, the agent uses the Balanced heuristic and reports a notice in the game log. The underlying cause of an individual malformed output is not always known; a token-limit stop is reported when Ollama provides it. Asynchronous requests are cancelled on a rewind or agent change and stale answers are discarded.

The local Vite bridge accepts only same-origin requests from a loopback client on a loopback host and talks only to `127.0.0.1:11434`; it is not a generic proxy. Ollama prompts include the acting bot's private hand, so use only a local Ollama installation you trust. No requests are sent to a cloud LLM by the application.

## Comparing bots

**AI Training Lab → Bot comparison** runs two selected policies in matched games: for each seed and each of five candidate seats, A and B separately receive the same initial setup, seat, deck, and opponent agents. Opponents and deck assignments are identical *within each pair*; play can diverge afterwards. One deal is 10 games. By default, the three playtest deck snapshots are repeated on the five-seat table. The Lab deck selector can instead use a pasted or saved full deck for the candidate against four full precons; see `docs/ml-training.md`. Neither setup is a universal measure of every VTES deck. Neural evaluation is greedy, without PPO exploration. The panel reports VP, wins, average time for non-forced decisions, and LLM request count. Cancellation or an error retains only completed pairs. **Resume previous comparison** restarts the incomplete pair with the same captured configuration and advances from the next pair. This is in-memory only: reloading the page or starting a new comparison discards it, and resuming cannot recover results from an earlier version of the page. A game that used Ollama fallback is not scored as an LLM game: the comparison stops with an error instead. To test the new card advice, compare **Ollama LLM (card guidance)** against **Ollama LLM (without card guidance)**. The latter is an ablation of the current prompt: it uses the same model, context-selection algorithm, bot guardrails, and system prompt, but omits the card-decision advice. It is not the exact old implementation. The report also shows the largest prompt-token count Ollama reported when available; a dash means no count was reported, and even a reported count does not prove the input was not truncated. Tiny samples are noisy and a fixed seed is not a substitute for independent evaluation. LLM outputs may not be reproducible even with identical initial seeds.

## Prompt, context and limitations

The bridge sends a system message that tells the model to play VTES for the acting seat, choose an offered ID, treat card text as data, pursue victory points by ousting prey, protect its own pool and minions, consider costs and the current action/combat/referendum, and not assume it sees hidden cards. The user message is JSON with the task, a few matching rules summaries, the masked seat and table view, current action/combat/referendum/pending card, the window, legal options and selected printed card texts. The exact messages are defined in `scripts/ollama-bridge.ts` and `src/ai/ollama-agent.ts`.

When a card can be played, the guided prompt explicitly asks the model to compare the benefit now with saving the card, the risk of passing, costs, and the value of cycling an awkward hand. Combat, action and cancel windows receive short situation-specific advice. This is advice rather than a hard play/pass rule; it neither predicts hidden replies nor guarantees a stronger decision. The existing influence and hopeless-block bot-only filters still apply, so the supplied choices are not always the engine's complete legal list.

The local catalogue supplies text for visible cards in priority order: pending/acting/referendum card, playable cards in the bot's hand, remaining hand, combatants and other public cards. The card-text allowance is 8,000 UTF-8 bytes; lower-priority texts may be omitted. Relevant rules are short summaries in the repository, not a full rulebook or a vector database. The prompt builder caps the serialized user message at 20,000 UTF-8 bytes, retaining the supplied options and essential masked state before adding optional card text, rules, and public ash heaps. Omitted ash heaps are marked as unknown, not empty. If the essential message alone exceeds the cap, the agent uses Balanced for that decision, reports the reason through the existing fallback notice, and tries Ollama again on the next decision. It does not send a shortened list of supplied options merely to fit the budget.

The request uses a 9,500-token context shared by input and output; the byte cap is only a conservative heuristic, **not model-specific tokenization**. The system message, output, JSON schema and tokenizer also affect capacity, so it cannot guarantee that Ollama won't truncate a prompt. During polling, known signed pool changes and seat relationships are explained explicitly; missing effects are marked unknown rather than assumed harmless. The model has no tool calls, search, game simulator, past-game memory, or deck-order knowledge. These inputs and strategic instructions have not been proven to improve playing strength: compare on fresh, matched seeds before concluding that they do.

During influence, the Ollama agent gets the capacity, current counters and remaining counters of its own uncontrolled vampires, with a short explanation of transfers. Its bot-only policy narrows ordinary pool transfers to the closest-to-completion vampire (ties remain choices), avoids spending down the pool on an unaffordable vampire, and avoids taking counters back while it can continue funding one at low pool. It normally keeps at least 3 pool; without a ready minion it can spend below that if it can finish a vampire with its current pool, account for the known entry tax, and retain at least 1 pool. Crypt draws are suppressed at 4 pool or less. A fully funded vampire is moved to ready automatically when only ordinary influence choices are present, no known entry tax applies and no visible copy is contested; otherwise the model can decide. Card abilities and passing remain available. The same policy applies to the Balanced fallback. These are imperfect strategic guardrails, not VTES legality rules or a guarantee of survival: they do not model future pool gains, all card effects, entry hazards, threats or every contest, and can make poor choices in unusual situations. Humans retain all legal options.
